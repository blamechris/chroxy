# CD CX and CY harness diagnostic report

## Finding and practical meaning

**CY has demonstrated useful implementation and continuation capability, but the retained evidence does not yet establish it as a replacement for CD or CX as the autonomous coordinator of a complete prime-directive run.** Productive CY workers contributed to four merged packages, including recent native Codex work. Those deliveries depended on CX coordination, review, acceptance and, in some cases, later corrections. Counting their whole packages as exclusively CY successes would hide the very dependency this evaluation is meant to measure.

**CD has the broadest verified multiwave delivery record in this sample; CX has verified delivery plus substantial recent owner-path acceptance work. Neither has earned an unconditional autonomy verdict.** The CD Chroxy chain contains 123 verified PD merges across 30 waves; CX's 14 recent desktop roots contain 19 verified merges across nine delivery-bearing chats, alongside coordination, investigations and incomplete QA. These are different workloads and observation periods. The numbers establish delivered work, not comparative intelligence, speed or user value.

**A defensible cost or reliability winner cannot be calculated from these runs.** The records mix models, risk, project maturity, permission rules, review depth and human waits. Accounting has material defects: stale ledger endpoints, a Claude rate-card discrepancy, missing child output, unpriced models, and stale Codex cumulative counters. This report repairs the measurements it can, retains historical figures as historical, and does not manufacture an all-in bill or a composite score.

The strongest next move is a bounded CY-coordinated trial using the now-proven worker routes, with a declared budget, an actual timeout test and complete parent/child accounting. This recommendation serves the [Core Goal](/Users/blamechris/Obsidian/no-it-all/coordination/Core%20Goal.md): ordinary work should move into Chroxy, with agents finding basic usability failures before Chris has to. No trial, runtime change or future automation was launched by this evaluation.

## Recommended next evaluation and product priorities

**First, make progress and recovery observable in CY.** A user should be able to tell whether work is running, waiting on a permission, blocked by account/model availability, waiting on CI, paused by policy or actually stopped. Test an intentionally delayed tool/job, require the configured bound to produce a terminal event, and verify no child remains after cleanup. The historical fixes may already cover parts of this; verify the shipped route rather than filing a duplicate from an old incident.

**Second, run a controlled CY coordinator trial before another broad feature wave.** Use a bounded queue with the same project base, observable acceptance, review gate and preauthorized scope as a CD or CX comparison run. Keep provider/model/effort fixed when isolating harness effects. Also permit a separately labeled “best configured stack” comparison when the real question is the experience Chris can obtain from each product today. Do not mix these two estimands.

**Third, complete a full ordinary-work acceptance loop.** The proof should include startup/auth, requested-versus-observed model, one permission round trip, a visible child outcome, a CI wait/resume, review and gated delivery, restart/context recovery, Stop targeting, notification routing and durable handoff. A runtime PASS from an older head should be rerun or explicitly retained as historical. Include one adversarial interruption to establish recovery instead of relying on a happy-path demo.

Use randomized or rotated harness order across more than one small task and more than one PD queue. Reset to isolated equivalent baselines. Avoid giving later runs the earlier solution or reviewer findings. Blind post-run adjudication where practical, and retain failed attempts and open runs. Start with a few repeats for feasibility; do not claim statistical superiority from one task per harness.

The next report should present a vector rather than one score: accepted outcomes, verified merges, wall time to acceptance, categorized owner interventions, retry/review work, observable usage by role, process incidents, and escaped defects after a fixed observation period.
